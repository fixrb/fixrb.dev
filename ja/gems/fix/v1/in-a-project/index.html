プロジェクトで使う

仕様をどこに置き、どうコードを読み込むか。そして実行するときに知っておくべきこと。

このページでは、libに商品とカートを、fixにその仕様を置いた小さなプロジェクトを使います。

配置

コードは、もともと置かれているlib/product.rbとlib/cart.rbに置きます。

Product = Data.define(:name, :price)

require_relative "product"

class Cart
  def initialize(*products)
    @products = products.freeze
  end

  def count = @products.size
  def total = @products.sum(&:price)
  def add(product) = Cart.new(*@products, product)
end

仕様はそれぞれfixの中に専用のファイルをもち、fix/product_fix.rbやfix/cart_fix.rbのように、対象にちなんだ名前をつけます。プロジェクトが大きくなればサブディレクトリを使います。ファイルはFixとテストするコードをrequireし、仕様を書き、サブジェクトをテストします。

require "fix"
require_relative "../lib/product"

Fix :Product do
  on :name do
    it MUST be_an_instance_of String
  end

  on :price do
    it MUST be_a_kind_of Numeric
  end
end

exit(Fix[:Product].test { Product.new(name: "Tea", price: 4) })

require "fix"
require_relative "../lib/cart"

TEA = Product.new(name: "Tea", price: 4)
CAKE = Product.new(name: "Cake", price: 6)

Fix :Cart do
  let(:products) { [] }

  on :count do
    it MUST eq 0
  end

  with products: [TEA, CAKE] do
    on :total do
      it MUST eq 10
    end

    on :add, TEA do
      on :count do
        it MUST eq 3
      end
    end
  end
end

exit(Fix[:Cart].test { Cart.new(*products) })

商品はファイルの定数です。withはファイルの読み込み時に存在する値をとり、letはサブジェクトごとに値を作ります。

コードの読み込み

上の例では、どのファイルもrequire_relativeでコードを読み込んでいます。これはどのディレクトリからでも、素のrubyでも動きます。ほかにもよく使われる方法が2つあります。

  • RUBYOPT=-Ilib fixはすべてのファイルのロードパスにlibを加えるので、ファイルはrequire "cart"と書けます。
  • Gemfileにgemspecと書いたgemでは、bundle exec fixがそのgemをロードパスに加えるので、ファイルは利用者と同じように名前でそれをrequireします。

複数の仕様ファイルが共有するファイル、つまりヘルパーや、ほかの仕様が求める仕様は、fixの中に_fix.rbで終わらない名前で置きます。そうすればfixがそれを単独で実行することはありません。パターンに例があります。

ほかのテストと並べる

Fixはほかのテストフレームワークに何も求めず、何も変えません。testのminitest、specのRSpec、fixのFixは、それぞれのコマンドで並んで動きます。Rakefileですべてを実行することもできます（task default: %i[test spec fix]と、sh "fix"を実行するタスクfix）。Fixの仕様は、matchi-fixを使えば、ほかのフレームワークのテストからマッチャーとして確かめることもできます。

プロセスが隔離しないもの

各コンテキストは子プロセスで実行されます。サブジェクトがプロセスの中で変えたもの、つまりグローバル変数、定数、カレントディレクトリ、ENVは子プロセスとともに消えます。プロセスの外で変えたものは残ります。書いたファイル、挿入した行、送ったメッセージです。

  • 各サブジェクトには、書き込む先を専用に与えてください。専用のディレクトリ、自分で作るデータベース、サービスの代わりになるオブジェクトなどです。サブジェクトブロックは期待ごとに実行されるので、そこが置き場所です。
  • 子プロセスは、開いているファイルや接続も含めて親のコピーとして始まり、それらを親と共有します。接続はファイルの中ではなく、サブジェクトブロックの中で開いてください。
  • ときどきfix --randomを実行してください。ある順では満たされ、別の順では満たされないファイルは、ほかのファイルが残していったものに依存しています。

デバッグ

デバッガーでサブジェクトの中で止めるには、そのコンテキストをプロセス自身の中で実行します（Fix[:Cart].test(fork: false) { … }）。このとき各コンテキストは前のコンテキストが残したものを目にするので、デバッグのあいだだけ使ってください。

SimpleCovのようなカバレッジツールは、プロセスが正常に終了したときに計測結果を保存します。Fixの子プロセスはexit!で終了し、この処理を飛ばすので、ツールが先に結果を保存しない限り、子プロセスで実行された部分は数えられません。プロセスについてはfixのREADMEに詳しく書かれています。
