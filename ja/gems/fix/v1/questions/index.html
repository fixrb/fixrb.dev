書く

Fix 1.0で動かないFixのコードを見つけました。

1.0より前のFixのために書かれたコードは、1.0で変わった語や省かれた語を使っていることがあり、その写しはいまも出回っています。1.0の最後のベータ版と、2024年から2025年にかけてのFix 0.19から0.21は、ほぼFix 1.0と同じように書けましたが、次の点は異なります。

1.0より前Fix 1.0では
gem install fix --pre, gem "fix", ">= 1.0.0.beta12"gem install fix, gem "fix"
最後の行にFix[:Duck].test { Duck.new }。testは失敗するとプロセスを終了させていたexit(Fix[:Duck].test { Duck.new })。testはtrueかfalseを返し、自分では終了しない。そのための括弧
eql, equaleq, be
be_empty、be_valid、have_key(:id)。どんな述語にも語があったon(:empty?) { it MUST be_true }というイディオム
letであるnameを使うit MUST eq name値は期待の中に、letはサブジェクトブロックの中に。期待の中のletを参照
Ruby 3.1以降、最後のベータ版は3.2以降Ruby 3.3以降とfork(2)

2014年から2019年までのFix 0.18以前は、別の言語でした。たとえば0.18では、Fix.describeがサブジェクトそのものをとり、期待はブロックでした（it { MUST eql "Swoosh..." }）。Fix 1.0では、サブジェクトを与えるのはテストです（Fix :Duck do … end、続いてexit(Fix[:Duck].test { Duck.new })）。1.0より前に書かれたブログの記事は、冒頭でその旨を断っています。

42.0を返すサブジェクトで、なぜit MUST eq 42が失敗するのですか？

eqはeql?です。数値に限らず、どの値についても、同じ値で同じクラスであることを求めます。1.eql?(1.0)はfalseで、"a".eql?(:a)もfalseです。クラスを問わず42に近い数値ならbe_within(delta).of(42)で、クラスだけならbe_a_kind_of Numericで比べてください。どちらもマッチャーにあります。

nameがletのとき、なぜit MUST eq nameと書けないのですか？

letはサブジェクトのパラメーターで、testのブロックとほかのletからしか見えません。期待の中で名前を使うと、サブジェクトが存在する前、ファイルの読み込み中に読まれることになるので、Fixは読み込み時にNameError（name is a let, visible in the subject block and in other lets only）を発生させます。値は期待の中に書き、letはサブジェクトブロックに読ませてください。test { "Hello, #{name}!" }に対してwith name: "Alice" do it MUST eq "Hello, Alice!" endと書きます。letとwithを参照してください。

let(:format)がArgumentErrorになります。なぜですか？

letは、サブジェクトブロックが実行されるオブジェクトのメソッドになり、そのオブジェクトからはKernelとトップレベルのメソッドが見えます。公開・非公開を問わずそれらと同じ名前のlet（format、p、test、open、select、method、class、hash…）や、言語の語（let、with、on、it、fix-itsを使うならits）、マッチャーやレベル（eq、match、change、fix、MUST）と同じ名前のletは、それを黙って再定義してしまいます。メッセージは持ち主か語を示します（format is already a method of Kernel）。別の名前を選んでください。

let(:items) { [] }とwith items: []の違いは何ですか？

letはブロックで、期待ごとに新たに呼ばれます。どの期待も新しい配列を受け取ります。withは値、つまり与えたオブジェクトそのもので、そのコンテキストの期待が共有します。with items: []は、どの期待にも同じ配列を与えます。2つのコンテキストは2つの子プロセスなので、共有がコンテキストを越えることはありません。

withで、宣言していないletの名前を使えますか？

使えます。withは、使った名前のletを宣言します。どのletも宣言していないキーは、エラーではなく新しいパラメーターになります。つまり綴りを間違えたキーは、黙って新しいletになります。綴りはサブジェクトブロックと照らし合わせてください。

ブロックをとるメソッドはどうテストしますか？

onのdo … endはコンテキストなので、onはメソッドをブロックなしで送ります。メソッドをサブジェクトブロックの中で呼ぶか（test { list.map { |x| x * 2 } }）、サブジェクトをsatisfy { |value| value.map { … } == … }で判定してください。

be_emptyやhave_key、be_validはありますか？

Fixの語としてはありません。イディオムはon(:empty?) { it MUST be_true }です。メソッドはonが送り、行にはexpected true to be trueと書かれます。runは、そのメソッドを結果のchainに.empty?として残します。とはいえmatch?とto_sをもつオブジェクトはどれもマッチャーなので、matchiのマッチャーを省略せずに書いたit MUST Matchi::Predicate.new(:be_empty)も動きます。独自のマッチャーを参照してください。

changeでletを監視できますか？

できません。マッチャーはファイルの読み込み時に作られるので、change(object, :method)のオブジェクトはその時点で存在している必要があります。letはそれより後にサブジェクトとともに存在するものなので、そこで名前を使うと、期待の中で読んだletと同じNameErrorになります。ファイルのオブジェクト、たとえば定数を監視してください。

it MUST fix(:Other)がKeyErrorになります。

fix(:Name)は文書が読まれるときに仕様を探すので、Fix :Otherはファイルのそれより前か、それより前にrequireしたファイルになければなりません。メッセージはno specification named :Otherです。登録済みの近い名前があれば、たとえばfix(:Positiv)に対する:Positiveなら、Rubyがその下にDid you mean?  :Positiveを加えます。仕様を組み合わせるを参照してください。

クラスメソッドやコンストラクターはどうテストしますか？

サブジェクトブロックからクラスを返し、onでメソッドを送ります。Fix[:Calculator].test { Calculator }にon :new, 2 do … endです。その中のonは、新しいインスタンスに送られます。

Ruby 3.4では、its(:size) { MUST eq it }がeq nilを作ってしまいます。

Ruby 3.4以降、ブロックの中の裸のitはブロックの暗黙のパラメーターです。要求をともなうitは、いまもFixの語です。3.3では裸のitはFixの語で、要求がないために例外を発生させます。値を書いてください。どちらのRubyでも使うsatisfyは、パラメーターに名前をつけます（satisfy { |value| … }）。詳しくはitsという語にあります。

判定

raise_exception ArgumentErrorがErrorではなくFailureになります。サブジェクトはTypeErrorを発生させました。

例外こそがraise_exceptionの判定するものです。別のクラスは偽となる照合なので、MUSTとMAYのもとではFailure、SHOULDのもとではWarningです。Errorとは、例外を判定するためのものではないマッチャーに例外が届いた場合のことです。eqなら、同じTypeErrorはErrorになります。

メソッドがないと、MAYではInfoなのに、MUSTではなぜErrorなのですか？

2つの問いがレベルを分けます。メソッドは存在するか。MUSTとSHOULDはそれを求め、MAYは求めません。仕様どおりに動くか。MUSTとMAYはそれを求め、SHOULDは推奨します。speakしないアヒルもon :speak do it MAY … endは満たします。5つの判定の表は仕様を書くにあります。

Warningがあると実行は失敗しますか？

いいえ。Success、Warning、Infoは成功として扱われ、FailureとErrorはそうではありません。Warningのある実行でもtestはtrueを返し、プロセスの終了ステータスは0です。

Ruby 3.4ではundefined method 'speak'、3.3ではundefined method `speak'と表示されます。

Rubyは3.4で引用符を変え、バックトレースのフレームはいまではメソッドのクラスも示します。これらの文はRubyのもので、Fixは書き換えません。

実行

なぜexit(Fix[:Duck].test { Duck.new })と括弧をつけるのですか？

括弧がないと、exit Fix[:Duck].test do … endはdo … endブロックをtestではなくexitに渡し、testはArgumentError（a block must be given）を発生させます。括弧を残すか、波括弧を使ってください。

仕様が2つあるファイルは、どう終了させますか？

すべてをテストしてから、一度だけexitします（exit([Fix[:A].test { … }, Fix[:B].test { … }].all?)）。

何も失敗していないのに、プロセスが1で終了します。失敗があるのに0で終了します。

ファイルの最後の行を見てください。testの結果をexitに渡し、それ以外のことはしていないはずです。testは決してexitを呼ばないので、それを忘れたファイルは何が起きても0で終了します。そしてfixコマンドはその終了ステータスしか読みません。仕様を実行するを参照してください。

ファイルをひとつだけ実行するには？　すべてを実行するには？

ひとつなら、ほかのRubyファイルと同じくruby fix/duck_fix.rbです。fix-command gemのfixは、fix/の*_fix.rbファイルを、あるいは与えたファイルとディレクトリを、それぞれ新しいプロセスで実行します（fix fix/duck_fix.rb fix/models）。

サブジェクトにlib/のロードパスが必要です。

コマンドは自分の環境をすべてのファイルに渡します。RUBYOPT=-Ilib fix、Gemfileのgemならbundle exec fixです。bundle execはgemをロードパスに加えるだけで、requireはしません。requireするのはファイルです。コードの読み込みを参照してください。

fixはファイルを並列に実行しますか？　タイムアウトはありますか？

1.0では、どちらもありません。ファイルはそれぞれ専用のプロセスで、ひとつずつ順に実行されます。Ctrl-Cはコマンドを終了させ、端末を通じて実行中のファイルも終了させます。

順序はランダムですか？

ファイルの中ではランダムではありません。コンテキストは書かれた順に、外側のものが内側のものより先に、毎回同じ順で実行されます。ファイルの間では、求めればランダムになります。fix --randomはファイルをシャッフルし、最初に、同じ順でもう一度実行するためのコマンドfix --random=2を書きます。ランダムな順序を参照してください。

サブジェクト自身の出力はどこへ行きますか？

サブジェクトが書いたものは、同じ標準出力に、そのコンテキストの行より前にそのまま出ます。改行のないまま残った文字列は、最初の行につながります。そのため、ランナーが読むのは行ではなく終了ステータスです。

SimpleCovが、サブジェクトが実行したコードについて何も報告しません。

各コンテキストは子プロセスで実行され、子プロセスはat_exitハンドラーを実行しないexit!で終了するので、SimpleCovが子プロセスの結果を書くことはありません。Fix自身のテストのように子プロセスが終わる前に結果を保存するか、計測のときはtest(fork: false)で実行してください。デバッグを参照してください。

FixはWindowsで動きますか？　JRubyでは？

動きません。Fixはコンテキストごとに子プロセスをforkするのでfork(2)が必要です。それがないRubyでは、期待をもつコンテキストがNotImplementedErrorを発生させます。CIでは、LinuxとmacOSで、Ruby 3.3、3.4、4.0、headをテストしています。

RSpecやminitestと並べて

テストスイートを置き換えなければなりませんか？

いいえ。Fixはほかのフレームワークに何も求めず、何も変えません。specやtestの隣にfixディレクトリを置いて専用のコマンドで実行し、Rakefileですべてを実行すればよいのです。Fixが担うのは、部品どうしが合意する振る舞い、つまりインターフェースや依存ライブラリとの契約です。テストスイートは、そのフィクスチャー、テストダブル、フレームワークをそのまま保ちます。その方法はほかのテストと並べるに、各イディオムが何になるかはRSpecからの移行にあります。

RSpecやminitestからFixの仕様を確かめられますか？

matchiのマッチャーとして確かめられます。matchi-fix gemのMatchi::Fix.new(:Duck).match? { Duck.new }は、Fixと同じようにコンテキストをforkして、trueかfalseを答えます。RSpecではexpect(Matchi::Fix.new(:Duck).match? { duck }).to be true、minitestではassert Matchi::Fix.new(:Duck).match? { duck }です。このとき失敗のメッセージはfalseと言うだけなので、行を見るにはFix[:Duck].test { duck }を使います。マッチャーのための仕様はwithなしで書きます。値は一度だけ与えられ、コンテキストがそれを作り直すことはできないからです。

失敗したfix(:Other)は、どの期待が失敗したかを教えてくれません。

そういう設計です。マッチャーはtrueかfalseを答えるものです。行を見るには、内側の仕様を単独でテストしてください（Fix[:Other].test { … }）。

結果を行ではなくデータとして得られますか？

Fix[:Name].run { … }はFix::ResultのArrayを返します。location、chain、outcome、passed?、summaryと、その下のSpectus::Resultをもつ、凍結されたデータです。testは、runに表示を加えたものです。データとしての結果を参照してください。

fix-itsのように、言語に語を加えるには？

onとitを組み合わせるメソッドをFix::Dslに加え、itには自分の呼び出し元のlocation:（caller_locations(1, 1).first）を渡します。そうすれば結果は仕様の行を指します。コード19行のfix-itsが手本です。

FixはRSpecやminitestとどう違いますか？

Fix、RSpec、minitestはそれぞれ別の仕事をするもので、ひとつのプロジェクトがそのうち2つを使うこともあります。違いは次のとおりです。
