RSpecからFixへ：よりシンプルなテストへの旅

2015年9月6日 · Cyril Kato

Fix 1.0より前に公開した記事の翻訳です。記事は書かれたときのまま残しており、例は以前のバージョンのgemを指していることがあります。Fix 1.0については、ガイドのRSpecからの移行をご覧ください。

シンプルさを求めて

FixとRSpecのような従来のテストフレームワークとの最も際立った違いのひとつは、その複雑さにあります。興味深いことを物語る数字を見てみましょう。

RSpecの構成要素（バージョン3.3）

  • rspec gem（7行）と、実行時の依存gem：
    • rspec-core：6,689行
    • rspec-expectations：3,697行
    • rspec-mocks：3,963行
    • rspec-support：1,509行
    • diff-lcs：1,264行

合計：17,129行

Fixの構成要素（バージョン0.7）

  • fix gem（148行）と、実行時の依存gem：
    • spectus：289行
    • matchi：73行

合計：510行

根本の考え方は単純です。テストフレームワークは、それがテストするコードより複雑であってはならない。コードの量のこの劇的な差（16,619行）は、ミニマリズムと明快さへのFixのこだわりを映しています。

実例での比較

方法の主な違いがわかる実例を見てみましょう。次のMonsterクラスを考えます。

class Monster
  def self.get
    {
      boo: {
        name: "Boo",
        life: 123,
        mana: 42
      },
      hasu: {
        name: "Hasu",
        life: 88,
        mana: 40
      }
    }
  end

  def get(id)
    self.class.get.fetch(id)
  end
end

RSpecの層を重ねる方法

require_relative "monster"
require "rspec/autorun"

RSpec.describe Monster do
  describe ".get" do
    subject(:monsters) { described_class.get }

    describe "#keys" do
      it { expect(monsters.keys).to eql %i(boo hasu) }
    end
  end

  describe ".new" do
    subject(:described_instance) { described_class.new }

    describe "#get" do
      subject(:monster) { described_instance.get(name) }

      context "with Boo monster" do
        let(:name) { :boo }
        it { expect(monster).to eql({ name: "Boo", life: 123, mana: 42 }) }
      end

      context "with Boom monster" do
        let(:name) { :boom }
        it { expect { monster }.to raise_exception KeyError }
      end
    end
  end
end

Fixの直接的なスタイル

require_relative "monster"
require "fix"

Fix.describe Monster do
  on :get do
    on :keys do
      it { MUST eql %i(boo hasu) }
    end
  end

  on :new do
    on :get, :boo do
      it { MUST eql({ name: "Boo", life: 123, mana: 42 }) }
    end

    on :get, :boom do
      it { MUST raise_exception KeyError }
    end
  end
end

主な違い

  1. メソッドの連鎖：Fixでは、クラスメソッドでもインスタンスメソッドでも、ひとつの式でメソッドを記述できます。そのためコードがより簡潔で読みやすくなります。

  2. 唯一の情報源：すべての仕様は、ルートで与えた記述対象のオブジェクトから導かれます。明示的なサブジェクトも暗黙のサブジェクトも要りません。記述対象のオブジェクトと記述したメソッドから導かれる、読み取り専用の動的なサブジェクトがひとつあるだけです。

  3. 一貫した構文：Fixは、何をテストするかにかかわらず同じ構文を保ちます。値を確かめるときも、エラーを期待するときも、状態の変化を確かめるときも、構文は統一されていて予測できます。

実践での明快さ

Fixは、より直接的で、儀式の少ないテストの書き方を促します。2つのフレームワークがエラーの確認をどう扱うかを比べてみましょう。

RSpec：

expect { problematic_call }.to raise_exception(ErrorType)

Fix：

it { MUST raise_exception ErrorType }

値の比較なら：

RSpec：

expect(value).to eq(expected)

Fix：

it { MUST eql expected }

この一貫性は認知的な負担を減らし、テストを書きやすく、理解しやすくします。

まとめ

Fixは、シンプルさと明快さを優先する、Rubyのテストへの新しい取り組みです。複雑さを減らし、一貫した構文を保つことで、開発者が大切なこと、つまりコードの振る舞いを確実に確かめる、明快で保守しやすいテストを書くことに集中できるようにします。

Fixを試してみたいですか？　まずはこちらから：

gem install fix

Fixでテストの流れをどう改善できるかは、ドキュメントをご覧ください。
