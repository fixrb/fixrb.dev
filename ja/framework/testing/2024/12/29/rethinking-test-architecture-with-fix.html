仕様を明確に分離してテストの設計を考え直す

2024年12月29日 · Cyril Kato

Fix 1.0より前に公開した記事の翻訳です。記事は書かれたときのまま残しており、例は以前のバージョンのgemを指していることがあります。Fix 1.0についてはガイドをご覧ください。

Rubyの開発の世界では、RSpecやMinitestのようなテストフレームワークが業界の標準になっています。しかしFixは、注目に値するまったく異なる方法を提案します。仕様とその実装を、きれいに分離することです。

従来の設計：関心事の混在

従来、Rubyのテストフレームワークは、期待する振る舞いの定義と、それを確かめる具体的なexampleを、同じファイルに混ぜてきました。RSpecの典型的な例を見てみましょう。

RSpec.describe Calculator do
  subject(:calculator) do
    described_class.new(first_number)
  end
  describe "when first number is 2" do
    let(:first_number) do
      2
    end
    context "#add" do
      let(:second_number) do
        3
      end
      it "adds two numbers" do
        expect(calculator.add(second_number)).to be(5)
      end
    end
  end
end

この例では、仕様（2つの数を足すこと）がセットアップとコンテキストの何層もの中に包まれ、「何を」（数を足すと5になるべき）と「どうやって」（インスタンスを作り、変数を準備する）が混ざっています。

Fixの方法：責任の明確な分離

Fixは、2つの側面をはっきり分けることで、まったく異なる考え方をとります。

  1. 仕様：期待する振る舞いを定める、純粋な文書
  2. テスト：その仕様を試す、具体的な実装

同じ電卓のテストは、Fixでは次のようになります。

# 1. The specification - a pure and reusable document
Fix :Calculator do
  on(:new, 2) do
    on(:add, 3) do
      it MUST be 5
    end
  end
end

# 2. The test - a specific implementation
Fix[:Calculator].test { Calculator }

違いは歴然としています。Fixの仕様は：

  • 簡潔：期待する振る舞いがわずか数行で表されている
  • 明快：コンストラクターからメソッド呼び出しへの流れがひと目でわかる
  • 純粋：何が起こるべきかだけを述べ、どう準備するかは述べない

この分離には、いくつかの大きな利点があります。

1. 仕様の再利用

仕様は、異なる実装をまたいで再利用できる自律した文書になります。同じ電卓の仕様で、同じインターフェースに従う限り、異なる電卓クラスをテストできます。

2. 隔離されたテスト

各テストは完全に隔離して実行できるので、デバッグがしやすくなり、テストコードの保守性も高まります。仕様と実装が分かれているので、何をテストするかを変えずに、どうテストするかを変えられます。

もう少し複雑な例

この分離が、もう少し込み入った場合にどう当てはまるかを見てみましょう。

# A generic specification for a payment system
Fix :PaymentSystem do
  with amount: 100 do
    it MUST be_positive

    on :process do
      it MUST be_successful
      it MUST change(account, :balance).by(-100)
    end
  end

  with amount: -50 do
    on :process do
      it MUST raise_exception(InvalidAmountError)
    end
  end
end

# Specific tests for different implementations
Fix[:PaymentSystem].test { StripePayment.new(amount: 100) }
Fix[:PaymentSystem].test { PaypalPayment.new(amount: 100) }

この例では、決済システムの仕様は汎用的で、異なる決済の実装に当てはめられます。実装の詳細ではなくインターフェースに焦点を当てることで、どの決済処理系でも果たせる、再利用可能な契約ができます。

実践での利点

この設計上の分離は、実践でいくつかの利点をもたらします。

  1. ドキュメント：仕様は、システムの期待する振る舞いを示す、明快な生きたドキュメントになる

  2. 保守性：テストの実装を変えても、仕様を変える必要はない

  3. 柔軟性：同じ仕様で複数の実装を確かめられるので、次のような用途に向いている：

    • クラスの異なるバージョンのテスト
    • サードパーティとの連携の確認
    • マイクロサービス間の一貫性の確保

  4. 明快さ：「何を」と「どうやって」を分けることで、仕様もテストも焦点が絞られ、理解しやすくなる

まとめ

Fixは、Rubyでのテストの書き方を考え直すよう促しています。仕様を具体的なテストからはっきり分けることで、次のことができます。

  • より明快で再利用できる仕様を作る
  • 期待を表す生きたドキュメントを保つ
  • 異なる実装を同じ仕様でテストする
  • 問題をより簡単に切り分ける

この独特な設計上の方法によって、Fixは、実装に大きな柔軟性を保ちながら、正確で再利用できる仕様を必要とするプロジェクトにとって、特に興味深い道具となっています。
