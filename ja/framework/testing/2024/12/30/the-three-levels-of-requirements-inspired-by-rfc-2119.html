RFC 2119に着想を得た3つの要求レベル

2024年12月30日 · Cyril Kato

Fix 1.0より前に公開した記事の翻訳です。記事は書かれたときのまま残しており、例は以前のバージョンのgemを指していることがあります。Fix 1.0については仕様を書くをご覧ください。

ソフトウェア開発では、言葉の正確さが欠かせません。テストの仕様を定めるときは、なおさらです。FixはSpectusライブラリを通じて、RFC 2119に直接着想を得た3つの要求レベルを導入し、仕様に豊かでニュアンスのある意味をもたせます。

3つの要求レベル

MUST/MUST_NOT：絶対

MUSTレベルは、仕様の絶対的な要求を表します。MUSTを使うとき、その機能は必須で、譲れないものだと示しています。形式的には、MUSTを使ったテストが成功するには、期待が確実に満たされなければなりません。期待が満たされなければ、テストは無条件に失敗します。

Fix :Password do
  it MUST_NOT be_empty
  it MUST have_length_of(8..128)

  with content: "password123" do
    it MUST include_number
    it MUST_NOT be_common_password
  end
end

この例では、MUSTをつけたテストはどれも、破ることのできない規則を表しています。空のパスワードや短すぎるパスワードは、単に受け入れられません。これらの条件のどれかが満たされなければ、ほかの事情にかかわらずテストは失敗します。

SHOULD/SHOULD_NOT：推奨

SHOULDは強い推奨を表します。特定の状況では無視してもかまいませんが、その影響を理解し、慎重に評価しなければなりません。技術的には、SHOULDをつけた期待が満たされなくても、例外が発生しなければテストは成功しえます。これにより、任意だが推奨される機能を、穏やかに劣化させることができます。

Fix :EmailService do
  on :send, to: "user@example.com" do
    it MUST deliver_email
    it SHOULD be_rate_limited
    it SHOULD_NOT take_longer_than(5.seconds)
  end
end

ここでは、メールの配信は必須（MUST）ですが、レート制限は強く推奨される（SHOULD）だけで、特定の状況では無効にできます。レート制限の確認が満たされなくても例外が発生しなければ、テストは成功します。推奨には従っていないものの、システムは期待どおりに動いていることを示しているのです。

MAY：任意

MAYは、本当に任意の機能を表します。Fixの実装では、MAYの要求には独特の振る舞いがあります。テストは、期待が満たされた場合か、NoMethodErrorが発生した場合のどちらかで成功します。これで、任意の機能がまったく実装されていない場合をうまく扱えます。状況によって実装が異なるかもしれない機能や、まったく実装されないかもしれない機能を仕様に書くときに、特に役立ちます。

Fix :UserProfile do
  on :avatar do
    it MUST be_valid_image
    it SHOULD be_less_than(5.megabytes)
    it MAY be_square
    it MAY support_animation
  end
end

この例では：

  • アバターは有効な画像でなければならない（MUST）。満たされなければ失敗する
  • 軽量であるべきである（SHOULD）。例外なしに満たされない場合は成功する
  • 正方形であってもよい（MAY）。次のどちらかなら成功する：
    1. 期待が満たされた（アバターが正方形である）
    2. 正方形かどうかを確かめるメソッドが実装されていない（NoMethodErrorが発生する）
  • 同じく、アニメーションへの対応は任意で、まったく実装されていなくてもかまわない

この3つのレベルの仕組みによって、実装の柔軟さを保ちながら、要求を正確に仕様にできます。3つのレベルがすべて一緒に働く、もう少し複雑な例を示します。

Fix :Document do
  # Absolute requirements - must pass their expectations
  it MUST have_content
  it MUST have_created_at

  # Strong recommendations - can fail without exception
  it SHOULD have_author
  it SHOULD be_versioned

  # Optional features - can be unimplemented
  it MAY be_encryptable
  it MAY support_collaborative_editing

  on :publish do
    it MUST change(document, :status).to(:published)  # Must succeed
    it SHOULD notify_subscribers             # Can fail gracefully
    it MAY trigger_indexing                  # Can be unimplemented
  end
end

歴史的な変遷：RSpecからFixへ

この意味論的な方法は、RSpecの歴史とは対照的です。RSpecはもともと、キーワードshouldを主なインターフェースとしていました。

# Old RSpec style
describe User do
  it "should validate email" do
    user.email = "invalid"
    user.should_not be_valid
  end
end

しかし、この方法にはいくつかの問題がありました。

  • shouldを加えるためにObjectをモンキーパッチすると、衝突が起こりうる
  • 絶対的な要求にshouldを使うのは、意味として誤っていた
  • グローバルな名前空間が汚れ、コードの保守が難しくなった

RSpecは最終的にexpect構文へ移行しました。

# Modern RSpec
describe User do
  it "validates email" do
    user.email = "invalid"
    expect(user).not_to be_valid
  end
end

Fixの方法：明快さと正確さ

Fixは、RFC 2119の意味を全面的に取り入れることで、別の道を選びます。3つのレベルすべてを示す完全な例です。

Fix :Article do
  # Absolute requirements
  it MUST have_title
  it MUST have_content

  # Strong recommendations
  it SHOULD have_meta_description
  it SHOULD be_properly_formatted

  # Optional features
  it MAY have_cover_image
  it MAY have_comments_enabled

  on :publish do
    it MUST change(article, :status).to(:published)
    it SHOULD trigger_notification
    it MAY be_featured
  end
end

# Test against a specific implementation
Fix[:Article].test { Article.new(title: "Test", content: "Content") }

この方法にはいくつかの利点があります。

  • 要求レベルごとに明快で正確な意味がある
  • グローバルなモンキーパッチがない
  • 開発者の意図を正確に映す、生きたドキュメントになる
  • 標準化された語彙で、チームのコミュニケーションがよくなる

まとめ

Spectusから受け継いだFixの3つの要求レベルは、テストの期待を表す、強力でニュアンスのある方法です。仕様と実装の明確な分離と組み合わさって、Fixは保守しやすく、意図の伝わるテストを書くのに特に向いています。

RSpecの変遷は、正確な意味ときれいな設計の大切さを教えてくれます。Fixはその教訓を生かしながら、Rubyのテストに現代的で洗練された方法をもたらします。
