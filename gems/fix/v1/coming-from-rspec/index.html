Fix guide, version 1

Coming from RSpec

The same ideas under other names, and a few left out on purpose.

RSpec and Fix both describe behaviour with nested contexts and expectations. Two things differ at the root. A specification of Fix names no class: the subject comes from the test, on the last line, so that the same specification can test another one. And a specification is a document, read once when the file is loaded: it holds no code that runs before or after an expectation.

An RSpec spec of a counter, with a subject, a before that increments it in one context and a let overridden in another, becomes:

require "fix"

class Counter
  attr_reader :count

  def initialize(start) = @count = start
  def increment = tap { @count += 1 }
end

Fix :Counter do
  let(:start) { 0 }

  on :count do
    it MUST eq 0
  end

  on :increment do
    on :count do
      it MUST eq 1
    end
  end

  with start: 5 do
    on :count do
      it MUST eq 5
    end
  end
end

exit(Fix[:Counter].test { Counter.new(start) })

ruby counter_fix.rb
counter_fix.rb:14: Success: expected 0 to eq 0
counter_fix.rb:19: Success: expected 1 to eq 1
counter_fix.rb:25: Success: expected 5 to eq 5

The before became a method of the chain: increment returns the counter, and count is sent to it. A method that needs some preparation beyond a chain gets it in the subject block, from the lets.

Three levels instead of pending

RSpec skips an example, or marks it pending so that its failure does not fail the run. Fix says it in the specification itself: SHOULD for what is recommended, a warning when it is not met; MAY for what is optional, an info when the method does not exist. Both pass, and both are written in the lines, so nothing is hidden. Writing specifications has the five outcomes.

Left out on purpose

  • Hooks, before, after, around: the subject block builds what a subject needs, for each expectation, and each context runs in a process of its own, so there is nothing to clean up in memory.
  • Doubles and mocks, double, allow(…).to receive: give the subject a real object, or a small object of the file that stands for a service, through a let. A specification says what a subject does, not which messages it sends.
  • Shared state between examples, before(:all), instance variables: a let lives with one subject, and a context cannot reach another; only a with shares its value, within its context.
  • Tags and filters, focus: fix takes files and directories, and a file is a program that can be run alone.
  • aggregate_failures: every expectation gets its line, met or not.

Both can live in one project, each in its directory: In a project tells how.
